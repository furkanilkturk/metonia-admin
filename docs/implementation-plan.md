# Metonia Admin implementation plan

## Purpose and delivery rule

This plan turns the accepted product scope and ADRs into an implementation order. It is deliberately narrow: the first complete proof is one generated, native SvelteKit application, not a set of partially implemented combinations.

The first release candidate path is:

```text
Standard SvelteKit + shadcn-svelte + one verified shadcn-svelte theme
+ Zod + Drizzle + generic PostgreSQL + Dashboard, Users, and Settings
```

The first generated-project package-manager candidate should be Bun because it keeps the initial proof close to the Bun-first monorepo, but it is not labelled Stable until its own generated-project integration gate passes. Docker is off for the first proof and follows as an optional path. Other package managers and Remote Functions follow only after the primary path is green. Fluid UI, provider-specific databases, authentication, deployment adapters, and maintenance commands are outside this plan's MVP delivery path.

Nothing generated by this plan may require a Metonia runtime at application build time or runtime. The generated application owns ordinary SvelteKit source, dependencies, scripts, and configuration.

## Proposed restrained monorepo shape

The current root workspace remains Bun-first. Add packages only where a stable ownership boundary exists; do not create a package for every recipe or every future adapter.

```text
apps/
  website/                         # public documentation and configurator
  reference-admin/                 # generated canonical app; output, never hand-edited
packages/
  registry/                        # capability catalog, config schema, resolver, compatibility
  generator/                       # transactional pipeline, recipes, source assets, adapters
    src/
      contracts/
      core/
      recipes/
        base/
        architecture/
        admin-core/
        documents/
        data-patterns/
      adapters/
        package-managers/
        ui/
        validation/
        orm/
        database/
        docker/
    assets/                        # small shared source assets, never combination templates
  cli/                             # interactive/non-interactive command boundary and output
tests/
  unit/
  contract/
  generator/
  integration/
fixtures/
  generated/                       # generated snapshots/contract fixtures only
docs/
  research/                        # dated authoritative ecosystem evidence
```

`packages/registry`, `packages/generator`, and `packages/cli` are the only required initial packages. The source package for the CLI can use an internal workspace name while the public distribution name and executable remain a publication research gate; do not assume that `create-metonia-admin` is publishable until that gate is closed. A future adapter becomes its own package only if it has independent consumers, release cadence, or ownership that makes that boundary useful.

`apps/reference-admin` and `fixtures/generated` are generator outputs. Their source of truth is a checked-in resolved configuration and the generator. A contributor changes recipes, reruns the documented regeneration command, and reviews the generated diff; they never edit output files to repair a fixture.

### Recipe and template shape

Recipes compose a staged project in this order:

```text
SvelteKit base
  -> Metonia architecture
  -> admin core
  -> UI adapter and theme
  -> data-pattern boundary
  -> validation
  -> ORM and database
  -> Docker
  -> selected resources
  -> generated documents
```

The generator may use the currently verified SvelteKit project-creation mechanism for the base stage, then applies small, feature-owned file contributions and transforms. `assets/` contains common document fragments and narrowly shared source assets. It must not contain copied full applications such as `standard-shadcn-zod-drizzle-postgres`, and recipes must not multiply by every package-manager/theme/data-pattern crossing. The Standard and Remote recipes differ only in boundary glue; Dashboard, Users UI, shared contracts, services, repositories, navigation, and layout remain shared.

The generated application has this minimum shape:

```text
src/
  lib/
    client/
      ui/{components,views,pages}/
    server/
      db/
      repositories/
      services/
    shared/
      schemas/
      types/
      constants/
      utils/
  routes/
    (admin)/...
metonia-admin.config.ts
README.md
AGENTS.md
.env.example
```

The concrete SvelteKit filenames, current `sv` invocation, shadcn-svelte initialization, Drizzle driver/migration files, and Remote Function module conventions are ecosystem gates. This plan intentionally does not guess them.

## Public contracts and dependency direction

The following contracts are small, typed, and one-way. They are the integration points that later workstreams must preserve.

| Producer | Public contract | Consumers | Boundary rule |
| --- | --- | --- | --- |
| `packages/registry` | `CapabilityRegistry`, status metadata, theme ownership, `RawConfig`, versioned `ResolvedConfig`, `resolveConfig`, `validateCompatibility`, conditional-choice model, and a serializable configurator catalog | CLI, generator, website, tests | Has no dependency on CLI, generator, apps, or external command execution. |
| Registry resolver | Canonical capability IDs and a structured issue/result envelope | CLI and generator | Resolve aliases at the CLI edge; serialize canonical IDs only. Invalid/Unknown/Unsupported selections fail before generation. |
| `packages/generator` core | `GenerateRequest`, stage IDs, recipe contribution protocol, package-manager command plan, and `GenerateResult` | CLI, generator/integration tests | Accepts a **resolved** config, stages writes, and never asks prompts or decides capability status. |
| Generator recipes/adapters | File, dependency, script, transform, document-fact, and check contributions keyed by registry IDs | Generator core only | An adapter cannot add a selectable capability or change status; it implements an already-approved registry contract. |
| `packages/cli` | Interactive wizard, flags, no-TTY behavior, exit semantics, and a versioned JSON result envelope | End users and automated callers | Depends on registry and generator; it owns presentation, never recipe logic. In `--json` mode stdout contains exactly one result and all human diagnostics go to stderr. |
| `apps/website` | Public configurator and compatibility display built from the serializable registry catalog | Public visitors | Imports registry data only. It does not import generator recipes, duplicate option lists, or claim a status unsupported by the registry. |
| Generated project | Plain SvelteKit source, selected external dependencies, scripts, generated docs, and a literal config object | Generated-project owner; future maintenance CLI | It imports no Metonia package. `metonia-admin.config.ts` is a standalone exported literal (no Metonia type/runtime import). |
| Fixtures/reference app | Resolved config plus generator-produced output and assertions | Tests and documentation review | They are generated, not templates or hand-maintained implementation sources. |

### Configuration contract

The registry owns a versioned configuration shape with separate fields for package manager, UI adapter, UI-owned theme, data pattern, validation, ORM, database dialect/provider/driver, Docker, and starter resources. The product-facing CLI aliases `standard` and `remote-functions` resolve to the ADR canonical IDs `sveltekit-standard` and `sveltekit-remote-functions`; the generated config uses canonical IDs.

Public support vocabulary is `stable`, `experimental`, `unsupported`, and `unknown`. A research blocker is metadata explaining why a capability is `unsupported` or `unknown`, not a fifth status that can accidentally be treated as selectable. Theme IDs are nested under their UI adapter; there is no global theme collection.

`ResolvedConfig` is the only config handed to the generator. It includes the selected values, defaults actually applied, support warnings, and configuration schema version. The generator renders `metonia-admin.config.ts`, README, AGENTS.md, `.env.example`, scripts, and website-facing facts from this one object. That prevents a Bun command from leaking into a pnpm project, an unlabelled Remote project, or a cross-adapter theme from appearing in generated output.

### Generator contract

The generator runs these phases:

1. Parse input and resolve configuration without filesystem writes.
2. Validate capability status, ownership, compatibility, destination safety, and requested options.
3. Create a private staging directory on the destination filesystem, preferring an out-of-workspace system temporary directory and falling back to the destination parent when required for atomic publication.
4. Run ordered recipe stages and collect contributions/checks.
5. Render generated documents from the resolved config and validate the staged tree.
6. Publish the completed staging tree to the destination using the safest same-filesystem finalization available.
7. Optionally run the selected package-manager install and Git initialization as explicit post-generation operations, reporting their stage separately.

Any failure returns a stable stage ID and safe diagnostic, leaves the requested destination absent or unchanged, and removes only staging directories that this run created. A stage cannot recursively clean a user-selected parent or existing project. The core records enough structured data for the CLI JSON result and integration logs without placing decorative terminal output into machine output.

## Workstreams

All paths below are planned ownership boundaries. A workstream may modify only its listed source areas except for an agreed integration handoff. Co-located tests are preferred for package-local behavior; the QA workstream owns cross-package test trees and generated fixture regeneration.

### W0 — authoritative research and support gates

- **Scope:** Establish the factual basis for every external integration before implementation or promotion. Research is evidence collection, not a reason to preselect unsupported options.
- **Owned files/directories:** `docs/research/**` only; it does not edit ADRs, registry entries, recipes, or product docs without a separate decision handoff.
- **Dependencies:** None.
- **Inputs:** Product specification, MVP scope, QA strategy, ADRs 0001–0010, and current primary-source documentation.
- **Outputs:** Dated research notes with source links, versions/dates checked, exact supported/experimental/unsupported/unknown conclusion, unresolved questions, and a proposed test command or observable behavior for each gate.
- **Acceptance criteria:** Research covers the SvelteKit base creation and Standard boundary APIs; shadcn-svelte initialization, alias, theme, CSS, and component flow; Zod and Drizzle/PostgreSQL driver/migration guidance; Bun generated-project commands; Docker/SvelteKit runtime guidance; and the Remote Functions API/status before that path is enabled. Fluid UI remains unavailable without authoritative sources.
- **Risks:** Upstream API drift, sparse/ambiguous third-party documentation, unverified CLI publication names, and a local result being mistaken for portable support. Mitigate by recording source dates, command versions, and the exact promotion gate.

### W1 — Bun workspace and build foundation

- **Scope:** Turn the bootstrap root into a minimal Bun workspace for the three required packages and the website, with reproducible root quality commands.
- **Owned files/directories:** Root `package.json`, `bun.lock`, `bunfig.toml`, `tsconfig.json`, `.gitignore`, shared base config files, and package manifests. It does not own package source, recipes, or generated output.
- **Dependencies:** W0 only for any external tool/version decision; internal workspace setup may begin while research runs.
- **Inputs:** ADR 0001, the root engineering constitution, and the package/app shape above.
- **Outputs:** Workspace scripts that retain `bun run check`, `bun run lint`, `bun test`, `bun run build`, `bun run test:generator`, and `bun run test:integration`; package skeletons; and one source of shared TypeScript/test configuration.
- **Acceptance criteria:** The root uses Bun and only `bun.lock`; the workspace does not pretend that generated-project package managers are monorepo managers; empty package skeletons participate in the root quality commands; and no extra package is added without an ownership justification.
- **Risks:** Package/config churn can block parallel work. Keep root scripts thin and move package behavior into its owner package; make root-script/CI changes through the integration handoff rather than editing them from feature workstreams.

### W2 — registry and resolved configuration

- **Scope:** Implement the single typed catalog, capability status model, default resolution, compatibility rules, and serializable catalog consumed by every other product surface.
- **Owned files/directories:** `packages/registry/**`, including its co-located tests and public exports. It does not own CLI flags, generator recipes, website UI, or generated fixtures.
- **Dependencies:** W1; W0 findings are required before a capability is promoted or an external detail is encoded as supported.
- **Inputs:** ADRs 0005, 0006, 0008, 0009, and 0010; product support-status vocabulary; initial default-stack decision.
- **Outputs:** Canonical IDs; status/blocker metadata; UI-to-theme ownership; `RawConfig`/`ResolvedConfig`; deterministic defaults; compatibility validation; conditional selection descriptors; and a public serializable configurator model.
- **Acceptance criteria:** Unknown IDs, cross-adapter themes, Unsupported selections, and unresolved combinations fail deterministically; UI selection filters themes; all material choices survive resolution; Standard is the default data pattern; Remote is explicitly Experimental only when its evidence exists; Fluid is hidden/rejected truthfully; and generated-config round-trip tests pass.
- **Risks:** Registry becomes a second recipe engine or option lists are duplicated downstream. Keep it declarative and external-command-free; downstream consumers adapt the registry rather than extending it locally.

### W3 — transactional generator kernel

- **Scope:** Build the pipeline that receives a resolved configuration, manages staging/finalization, orders recipes, aggregates dependencies/scripts/doc facts, and reports structured stage results.
- **Owned files/directories:** `packages/generator/src/contracts/**`, `packages/generator/src/core/**`, and their co-located tests. The designated generator integration owner alone edits `packages/generator/src/recipe-plan.ts` (or its equivalent ordered-stage manifest).
- **Dependencies:** W1 and the W2 public contract. W0 must close the base-project creation gate before a real SvelteKit base stage is implemented.
- **Inputs:** `ResolvedConfig`, recipe/adaptor contract, ADR 0004, and QA staging requirements.
- **Outputs:** Stage IDs, staging lifecycle, safe path validation, atomic-finalization fallback policy, recipe execution context, command-plan collection, document-fact collection, and `GenerateResult`.
- **Acceptance criteria:** Configuration validation occurs before writes; failure injection leaves no partial destination; existing non-empty destinations are not overwritten; paths with spaces/Unicode/Windows separators are supported; cleanup is constrained to the private staging directory; and errors identify the failed stage without leaking secrets.
- **Risks:** Filesystem rename semantics differ across platforms and recipes may assume a shell. Keep core operations in Bun/TypeScript APIs where possible, stage under the destination parent, and test Windows separately from POSIX assumptions.

### W4 — CLI control surface

- **Scope:** Provide the creation command's interactive wizard, complete non-interactive flags, `--yes`, `--json`, diagnostics, and orchestration of W2/W3 contracts.
- **Owned files/directories:** `packages/cli/**`, including co-located parser/process tests. It may not edit registry option data, recipe code, root scripts, or public website files.
- **Dependencies:** W2 and W3. The public package/bin portability decision remains a W0 gate.
- **Inputs:** Registry choice model, config resolver, generator request/result, CLI acceptance criteria, and support status metadata.
- **Outputs:** Interactive conditional prompt flow; deterministic flags; explicit Experimental warning/confirmation behavior; a versioned machine result envelope; meaningful exit codes; and stderr diagnostics.
- **Acceptance criteria:** Equivalent interactive, flag, and `--yes` choices resolve the same config; all material choices have non-TTY representation; `--json` writes exactly one parseable success or failure object to stdout; Remote explicit flags do not prompt; invalid input and failed stages exit non-zero with no final partial project; and selected package-manager documentation comes from its adapter plan.
- **Risks:** Terminal decoration corrupts JSON, prompt libraries leak TTY assumptions, and distribution portability differs from local Bun execution. Test actual subprocesses with and without TTY; do not claim `npx`/`pnpm dlx`/`yarn dlx` portability until W0/W10 evidence exists.

### W5 — base, architecture, admin-core, and generated-document recipes

- **Scope:** Produce the smallest bootable Standard SvelteKit project in the staged tree, overlay the locked architecture, add the common admin shell/navigation and Dashboard/Settings route-to-page composition, and render all configuration-aware documents.
- **Owned files/directories:** `packages/generator/src/recipes/base/**`, `architecture/**`, `admin-core/**`, `documents/**`, and `packages/generator/assets/common/**` / `assets/documents/**`. It contributes registered exports only; the W3 integration owner changes the ordered manifest.
- **Dependencies:** W0 SvelteKit gate, W2, and W3. W4 may exercise this path once the generator request is stable.
- **Inputs:** Resolved default config, verified base-project mechanism, document facts, ADRs 0002–0004, and the design-system master.
- **Outputs:** A native SvelteKit baseline with `$lib/client`, `$lib/server`, `$lib/shared`; thin `(admin)` route adapters; reusable admin shell/navigation; Dashboard/Settings page composition; literal `metonia-admin.config.ts`; README, AGENTS.md, and `.env.example` derived from the selected config.
- **Acceptance criteria:** Generated routes normally render one client page; client/server/shared and components/views/pages directories exist with one-way imports; there is no Metonia dependency or hidden runtime; docs agree with scripts and selected package manager; the unauthenticated baseline is clearly stated; and the standard path uses native SvelteKit boundary mechanisms rather than a parallel API.
- **Risks:** Treating the base creator's output as a long-lived copied template, document drift, or route screens growing into implementations. Keep base creation behind a recipe, generate docs from `ResolvedConfig`, and enforce thin-route/import-boundary assertions.

### W6 — shadcn-svelte adapter, theme, and Dashboard UI proof

- **Scope:** Implement only the researched shadcn-svelte adapter, one verified adapter-owned theme, and the accessible admin UI components/views/pages needed to make Dashboard the canonical composition example.
- **Owned files/directories:** `packages/generator/src/adapters/ui/shadcn-svelte/**`, `packages/generator/src/recipes/ui/shadcn-svelte/**`, and `packages/generator/assets/ui/shadcn-svelte/**`, with co-located adapter tests. It does not own registry metadata, general pipeline code, or generated fixture output.
- **Dependencies:** W0 shadcn-svelte gate, W2, W3, and W5.
- **Inputs:** Verified shadcn-svelte package/CLI/CSS/theme/alias evidence; the selected registry theme; design-system master; Dashboard composition contract.
- **Outputs:** Adapter install/configuration contributions, primitives mapped to `$lib/client/ui/components`, theme application, accessible admin shell components, Dashboard views/pages, and a reproducible UI adapter integration check.
- **Acceptance criteria:** The real adapter targets `$lib/client/ui/components` rather than an unrelated default alias; no global theme list exists; menus, dialogs, forms, tables, focus states, and responsive navigation meet the design/accessibility baseline; recipe trace is limited to composition-oriented surfaces; reduced motion is respected; and a generated project compiles with the verified upstream flow.
- **Risks:** shadcn-svelte CLI/theme behavior can drift and component generation may write outside the required architecture. Keep exact commands behind the adapter, pin/record research evidence, and fail the integration test if the alias or generated imports differ.

### W7 — Standard Users persistence path

- **Scope:** Complete the primary vertical slice: Zod schemas and server-boundary validation; Drizzle/generic PostgreSQL setup, migrations, repositories, and services; Standard SvelteKit loads/actions; and the Users CRUD resource. Settings remains a lightweight page example.
- **Owned files/directories:** `packages/generator/src/adapters/validation/zod/**`, `adapters/orm/drizzle/**`, `adapters/database/postgresql/**`, `src/recipes/data-patterns/sveltekit-standard/**`, `src/recipes/resources/users/**`, and their co-located tests. It contributes public recipe exports but does not edit W6 UI adapter assets or W8 fixtures.
- **Dependencies:** W0 Zod/Drizzle/PostgreSQL/SvelteKit Standard gates, W2, W3, W5, and W6.
- **Inputs:** Shared/server/client boundary rules, UI primitive contract from W6, selected generic PostgreSQL configuration, and the Users acceptance criteria.
- **Outputs:** Shared Users schemas/types/filter contracts; server-only database client, ORM schema, migrations, repository/service layer; thin native Standard route boundaries; reusable Users list/detail/form views/pages; guarded disable/delete flow; and generated environment/migration instructions.
- **Acceptance criteria:** Users supports list, search, filter, sort, pagination, detail, create, edit, and disable/delete as selected by the resource contract; browser mutation input is validated on the server; client code never imports DB/repositories/private env; raw DB errors do not reach the UI; real PostgreSQL persistence succeeds; and UI pending/empty/error/field-error states are accessible.
- **Risks:** Driver/migration assumptions, accidental schema duplication, and a UI component crossing into server behavior. Keep ORM-specific files under `$lib/server`, reuse safe shared schemas, use verified parameterized APIs, and exercise the real database in W8 before making a Stable claim.

### W8 — QA harness, generated fixtures, and primary-stack evidence

- **Scope:** Build the layered test harness and use it to prove the canonical Standard stack from fresh generation through real integration. It is the sole workstream that regenerates committed generated outputs.
- **Owned files/directories:** `tests/**`, `fixtures/generated/**`, `apps/reference-admin/**` as generated output, and test-only helpers. It never hand-edits generated app/fixture source and does not change recipes to make an assertion pass.
- **Dependencies:** W2–W7 for the full primary proof; it may build test utilities after W2/W3 contracts are stable.
- **Inputs:** QA strategy, resolved configs, generator/CLI results, generated projects, and environment research records.
- **Outputs:** T0–T5 test commands; registry/config/CLI contract tests; staging failure tests; canonical Standard and Docker-off fixture generation; import-boundary/thin-route/no-runtime checks; generated-project smoke/integration runs; PostgreSQL Users runtime evidence; and retained failure artifacts/logs.
- **Acceptance criteria:** Fixtures are regenerated from the generator into a temporary directory before comparison; canonical Standard fresh generation, install, check, test, and build pass with its selected package manager; Users persists against disposable PostgreSQL; negative configs never stage a final project; documents/config/scripts agree; Windows/non-TTY/JSON behavior is covered; and every report distinguishes mock, generated-project, and real-runtime evidence.
- **Risks:** Snapshot drift hides architecture regressions, integration environments are flaky, and fixture edits bypass the generator. Use structured assertions, disposable paths/databases, recorded tool versions, health checks rather than sleeps, and a regeneration guard that rejects manual fixture-only changes.

### W9 — optional Docker recipe and runtime proof

- **Scope:** Add the Docker-on variation to the primary stack without changing its application architecture or making Docker mandatory.
- **Owned files/directories:** `packages/generator/src/adapters/docker/**`, `packages/generator/src/recipes/docker/**`, and co-located tests. Docker-enabled fixture regeneration remains W8-owned.
- **Dependencies:** W0 Docker/SvelteKit runtime gate, W2, W3, W5, W7, and the Docker-off primary project proof.
- **Inputs:** Resolved Docker flag, verified base image/runtime/healthcheck/PostgreSQL image evidence, generated database contract, and document-fact contract.
- **Outputs:** Conditional Dockerfile, ignore file, compose configuration where appropriate, environment wiring, local PostgreSQL/health behavior, and Docker-aware README/AGENTS instructions.
- **Acceptance criteria:** Docker-off output has no Docker-only files or commands; Docker-on output contains only the justified files; the image builds from a clean generated context without secrets; app/database readiness and `DATABASE_URL` wiring work; and migration/Users checks run in the documented disposable path.
- **Risks:** Host Docker availability, container runtime/version drift, destructive cleanup, and conflating local database Docker with a production deployment promise. Record host/tool versions, validate cleanup targets, and keep provider-neutral deployment claims separate.

### W10 — generated-project package-manager adapters and CLI distribution

- **Scope:** Promote package-manager support one adapter at a time after the default path is proven. Start with the initial Bun generated-project adapter; add npm, pnpm, Yarn, or Deno only when each has independent research and evidence. Separately establish the published CLI distribution strategy.
- **Owned files/directories:** `packages/generator/src/adapters/package-managers/**` and their co-located tests; packaging/distribution metadata under `packages/cli/**` is changed through a coordinated W4/W10 handoff. It does not change root Bun tooling.
- **Dependencies:** W0 package-manager/publication research, W2, W3, W4, W5–W8. No later adapter can bypass the primary-stack release evidence.
- **Inputs:** Package-manager adapter contract (`install`, dependency changes, script execution, executable invocation, lockfile expectations), clean-environment logs, and generated document facts.
- **Outputs:** Per-manager command plans and lockfile behavior; registry status updates backed by evidence; package-manager-specific generated README/AGENTS commands; and documented CLI invocation support where verified.
- **Acceptance criteria:** For every Stable-labelled manager, a clean generated project succeeds at generate, install, check, test, and build with that manager, records OS/runtime/tool versions, and documents only that manager's commands. Deno is never renamed or implied as supported without its own research/integration run. A successful Bun proof does not promote another manager.
- **Risks:** A local package manager passes while fresh CI fails, generated package metadata differs across managers, and package publication names are unavailable. Keep unverified adapters Unknown/Unsupported, test clean temporary directories, and treat distribution/package-name decisions as release gates.

### W11 — Remote Functions experimental boundary variation

- **Scope:** Add the Remote Functions path only after official API verification and the full Standard primary stack is proven. Change boundary files only; do not fork the admin application.
- **Owned files/directories:** `packages/generator/src/adapters/data-patterns/remote-functions/**`, `packages/generator/src/recipes/data-patterns/sveltekit-remote-functions/**`, and co-located tests. W8 owns the regenerated `canonical-remote` fixture and integration report.
- **Dependencies:** W0 Remote Functions research, W2, W3–W8. It is intentionally after W7, not in parallel with the first end-to-end proof.
- **Inputs:** Current official Remote Functions filenames/exports/primitives/status, existing shared/server/client Users code, and the CLI Experimental-warning contract.
- **Outputs:** Route-local Remote boundary recipe, validation/error mapping, interactive warning data, generated Experimental labels, and a focused rollback/update note.
- **Acceptance criteria:** Remote modules validate public input and delegate to `$lib/server`; client UI does not import server/remote internals; Dashboard/Users/Settings UI, schemas, repositories, layout, and navigation remain shared with Standard; explicit non-interactive selection does not block; and a fresh primary-stack Remote project installs, checks, tests, and builds with an explicit Experimental label.
- **Risks:** Experimental upstream API changes and accidentally introducing a second client/server architecture. Keep Remote capability Experimental, locate it only at route/data boundaries, require current source evidence for every promotion run, and provide a clear disable/rollback path.

### W12 — website/configurator and public compatibility surface

- **Scope:** Build the public website and configurator only as a registry consumer, then surface the verified capability matrix, generated command preview, and product documentation without inventing an alternative configuration model.
- **Owned files/directories:** `apps/website/**` and its co-located tests/assets. It may import the registry's public serializable catalog but may not copy registry data or generator recipe logic.
- **Dependencies:** W2 for the catalog contract. Website shell/layout work may begin after W2; public Stable claims and command previews depend on W8/W9/W10 evidence.
- **Inputs:** Serializable registry catalog, resolved configuration preview, design-system master, support-status evidence, and generated-document facts.
- **Outputs:** Conditional configurator, UI-first theme filtering, status/Experimental disclosure, command/config preview derived from registry data, and accessibility/visual tests.
- **Acceptance criteria:** Changing UI changes only its owned theme choices; unsupported/unknown capabilities cannot appear as working selections; website status/command/config information matches registry output; the design uses the recipe trace only to explain composition; and responsive, keyboard, focus, contrast, and reduced-motion checks pass.
- **Risks:** A polished configurator makes unverified capabilities appear production-ready or duplicates CLI behavior. Treat it as a read-only registry projection, test its catalog contract, and make status warnings impossible to suppress in UI state.

### W13 — release integration and documentation alignment

- **Scope:** Assemble evidence into a release decision and synchronize public descriptions only after underlying proof exists.
- **Owned files/directories:** Root `README.md`, capability/status documentation outside `docs/research/**`, release/CI configuration, and final integration manifests. This workstream does not change ADRs or generated fixtures by hand.
- **Dependencies:** W8 and any relevant W9–W12 workstream. It is last for a capability promotion.
- **Inputs:** Test logs/artifacts, registry status changes, generated project outputs, website contract output, and W0 research notes.
- **Outputs:** Traceable release checklist, CI tier configuration, aligned CLI help/documentation status language, and explicit downgrade notes where evidence is missing.
- **Acceptance criteria:** Root Bun quality gates pass; every Stable claim links to a clean generated-project evidence run; generated README/AGENTS/config, CLI help, website, docs, and registry agree; unauthenticated starter limitations are explicit; and missing evidence leaves the capability Experimental, Unsupported, or Unknown rather than silently promoted.
- **Risks:** Documentation advances ahead of tests or a single environment is mistaken for general support. Make status changes review-sensitive and require attached evidence with environment/version details.

## Parallel work without overlapping files

Parallel work is permitted only after the listed public contract is accepted. Parallelism does not allow a later path to claim support before the primary proof.

| Wave | Workstreams that may proceed together | Non-overlap rule / synchronization point |
| --- | --- | --- |
| A | W0 research and W1 workspace | W0 owns `docs/research`; W1 owns root/workspace files. W1 consumes only already-recorded research conclusions. |
| B | W2 registry and W3 generator-core scaffolding | W2 owns the contract; W3 may implement against its reviewed interface but cannot alter registry types. Synchronize before W3 first imports the public package. |
| C | W4 CLI, W5 base/architecture/docs recipes, W12 website shell | They own `packages/cli`, their distinct generator recipe directories, and `apps/website` respectively. All consume W2/W3 exports; none edits the ordered recipe manifest. |
| D | W6 shadcn adapter and W8 test-harness scaffolding | W6 owns UI-adapter recipe/assets; W8 owns `tests/**`. Fixture regeneration waits until an integrated primary recipe exists. |
| E | After M3, W9 Docker implementation, W10 research/adapter preparation, and W12 configurator completion | W9/W10 own separate adapter directories; W12 owns the website. Promotion/integration runs are serialized by W8 so evidence is attributable to one resolved config. |
| F | W11 Remote implementation and W12 public Experimental presentation | W11 owns Remote recipe files; W12 owns website UI. Both consume the same W2 status data. Remote fixture generation and final claims wait for W8 evidence. |

The generator integration owner serializes changes to the ordered-stage manifest. The release integration owner serializes root scripts, CI, and public status documentation. Generated fixtures and `apps/reference-admin` are regenerated only after recipe integration; no parallel task hand-edits them.

## Decisions explicitly awaiting ecosystem research

These are gates, not blanks to fill with plausible code:

1. **SvelteKit and `sv`:** Current supported Svelte/SvelteKit versions, project creation command/API, Standard load/action guidance, adapter/runtime expectations, and Windows behavior.
2. **shadcn-svelte:** Authoritative package and CLI, non-interactive initialization/add flow, alias configuration for `$lib/client/ui/components`, CSS/Tailwind requirements, theme registry, icon integration, and accessible primitive behavior.
3. **Zod, Drizzle, and generic PostgreSQL:** Current supported package versions, safe driver choice, schema/migration/seed commands, environment naming, parameterized query patterns, and generated-project package-manager implications.
4. **Remote Functions:** Current Experimental status, route-local filename convention, exports/primitives, read/form/command CRUD mapping, input-validation behavior, build constraints, and rollback implications.
5. **Generated-project package managers:** Bun first, then npm/pnpm/Yarn/Deno command/lockfile/executable semantics; clean install/check/test/build behavior; and the published CLI's actual compatibility with `bunx`, `npx`, `pnpm dlx`, and `yarn dlx`.
6. **Docker:** Supported SvelteKit production adapter/runtime and image strategy, PostgreSQL image/healthcheck/volume details, environment wiring, and supported host/CI assumptions.
7. **Browser/accessibility tooling:** Chosen browser runner, axe or equivalent integration, screenshot baselines, and CI artifact retention. Until selected, accessibility requirements remain mandatory but exact automation is a tooling gate.
8. **Fluid UI and future providers:** Fluid UI package/docs/themes/CSS/components; Neon/Supabase provider/driver requirements; named deployment targets; and an authentication/threat-model design. These stay Unsupported or Unknown and are absent from functional generation until independently verified.

## Integration checkpoints and non-negotiable acceptance

Before the first default-stack Stable claim, the integrated system must demonstrate all of the following in a fresh temporary directory:

- A CLI invocation resolves the default Standard configuration from flags and `--yes`, rejects invalid IDs/theme ownership before writes, and emits a single valid JSON result when requested.
- The generator stages and publishes a native SvelteKit project with no Metonia runtime dependency or copied Cartesian-product template.
- The generated project uses `$lib/client -> $lib/shared <- $lib/server` and `components -> views -> pages -> routes`; routes are boundaries rather than screen implementations.
- A real researched shadcn-svelte integration targets `$lib/client/ui/components` and the admin shell/Dashboard follows the accessibility and responsive design baseline.
- Users CRUD validates at the server boundary, persists through Drizzle/generic PostgreSQL, uses guarded destructive actions, and does not expose database errors/private values.
- `metonia-admin.config.ts`, README, AGENTS.md, `.env.example`, scripts, CLI help, registry output, and website configuration agree on package manager, theme, data-pattern status, Docker selection, and deferred authentication.
- The selected generated-project package manager performs clean install, check, test, and build; the run records versions and logs. Root Bun commands pass separately.
- Generated fixtures/reference output are regenerated from the generator and reviewed as outputs, never repaired by hand.

Remote Functions, Docker, additional package managers, and all future adapters receive their own checkpoints on top of this proof. Their existence in the registry, a source fixture, a mock, or a successful file write is not release evidence.
